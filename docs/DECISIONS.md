| D-023 | IBM Plex Sans (Light/Regular/SemiBold) and Mono (Regular/SemiBold) TTFs bundled with the OFL licence. Carbon colour tokens (white, g100) are a minimal hand-written QSS; a full Carbon component set is deferred to M2. | M0 only needs an empty styled window. |
| D-024 | `avg_power_w` is the average power while the unit is in that mode **and switched on**; the effective average is `avg_power_w * duty_cycle_ratio`. **Confirmed by the owner (D-035).** | Spec lists both fields without defining how they combine. |
| D-025 | Field names carry the unit suffix (`_w`, `_wh`, `_hz`, `_kg`, `_m`, `_s`, `_k`, `_deg`, `_v`, `_a`, `_bps`, `_bit`, `_ratio`, `_db`, `_dbi`, `_dbw`, `_dbm`). Files may write "2.2 GHz" for such fields; it is converted with pint on load and saved as the canonical number. Plain numeric strings without a unit are rejected. | Constraint 17; D-006. |
| D-026 | Logarithmic units never convert implicitly to or from linear ones ("10 dBW" in a `_w` field is an error). dBW and dBm convert only into each other. pint is not used for log units. | The classic W/dBW spreadsheet failure. |
| D-027 | Pydantic models are the single source of truth; JSON Schemas are generated from them (`budget export-schemas`), committed in `src/budget_core/schemas/` and checked by a test. `jsonschema` is a dev dependency only, not runtime. Schemas describe the canonical form (numbers, not unit strings). | Fewer runtime dependencies than loading schemas at run time (revises ARCHITECTURE section 1). |
| D-028 | Files are saved in canonical form: model field order, sorted dict keys, 2-space maps, explicit `null`, no comments. A load-save round trip of a canonical file is byte-identical; comments in hand-edited files are lost on save. | Constraint 14; comment-preserving edits can come with the GUI editors if wanted. |
| D-029 | Problems and error messages contain field names, units, ids and allowed names, never values read from files (YAML syntax errors do not echo content either). | Constraint 11: CI logs must not leak controlled data. |
| D-030 | Unit ids are the file names in `units/`; spacecraft modes map unit id to power-mode name and must cover every unit (`UNIT_NOT_MAPPED` is an error). Scenarios, ground stations and links are not in the M1 schema. | Spec: a spacecraft mode maps every unit to one of its power modes. |
| D-031 | Example projects (`budget export-examples`, committed in `examples/`, checked for drift by a test) have every configuration number set to `value: null, source: TBD`, so they produce placeholder warnings by design. Maturity classes are neutral names (`class_a..c`). | Constraint 15. |
| D-032 | `load_project` returns no project when any error exists, and never raises for user errors. `budget validate` exits 1 on errors (also on warnings with `--strict`). | Keeps GUI and CLI on the same Problem list. |
| D-033 | Mass budgets are in v1 (owner request, supersedes the spec's out-of-scope line): static roll-up with maturity margins and limits, centre of gravity, moments of inertia, and mission phases with expendables. Folded into M2 as a second PR (M2b). Thermal and data storage stay out of scope. | Owner chose all four mass options and "fold into M2". |
| D-034 | `margin_policy` goes to schema v2 in M2b (`margin_ratio` -> `power_margin_ratio`, new placeholder `mass_margin_ratio`) with a migration; unit mass properties are optional new fields (no version bump needed). | Power and mass margins differ per maturity class; uses the migration framework as designed. |
| D-035 | M2 starts only after PR #2 (M1) is merged, so M2 gets a clean PR from `main`. D-024 is confirmed by the owner: effective average power = `avg_power_w * duty_cycle_ratio`. | Owner decisions. |
| D-036 | Thermal budgets are in v1 (owner request, supersedes the spec's out-of-scope line): dissipation and limits roll-up plus a steady-state lumped node model (hot and cold cases). Transient thermal is not in v1. New milestone M4b after M4. Data storage stays out of scope. | Owner chose "Dissipation and limits" and "Steady-state node model", new milestone after M4. |
| D-037 | `heat_dissipation_ratio` is an explicit per-mode field (1.0 unless the unit radiates RF or exports power); thermal environment fluxes, optical properties and case definitions ship as `Sourced` placeholders. | Constraint 15; energy conservation is not a standards value but must be visible, not hidden. |
| D-038 | M2 and M4b depend on each other only through the power modes: M2a (power) comes first, M4b reuses its dissipation data. Optional node heat capacity is reserved in the model. | Avoids a breaking change if transient thermal is added after v1. |
| D-039 | M4b inputs, owner delegated ("you decide"): no environment fluxes, optical properties or case definitions are invented. The tool ships templates with `source: TBD` placeholders; results that depend on them are marked incomplete. Units map to thermal nodes through an optional `thermal_node` field that defaults to a node named like the unit's subsystem. Hot and cold cases are named load cases entered in `config/thermal_environment.yaml`. When M4b starts, a list of candidate reference sources is proposed for a thermal engineer to verify; values stay `TBD` until then. | Constraint 15; the owner has no source for these numbers. |
| D-040 | Static power conventions (project convention, ECSS-E-ST-20C text not available, flagged `SOURCE_MISSING`): effective unit power = `avg_power_w * duty_cycle_ratio`; unit margin by maturity class; system margin on the sum of margined loads; then `P_source = P_load / (eta_converter * (1 - distribution_loss))` per bus. Peak power is the sum of unit peaks (all at once, conservative). A number that is a placeholder gives `n/a` in every result that needs it, never a silent zero. | Spec: margins and losses from config; constraint 15 and 16. |
| D-041 | Reports are built from one neutral `ReportDocument` (sections, tables, assumptions, provenance) rendered to XLSX (openpyxl) and PDF (ReportLab, bundled IBM Plex fonts). Byte-identical regeneration: the date comes from `--date`/`SOURCE_DATE_EPOCH`, the user from `--user`/`BUDGET_USER`, ZIP timestamps are normalised, ReportLab runs with `invariant=1`. | Constraints 14 and 19. |
| D-042 | M2a GUI: project open, tree, Problems panel with jump to a YAML editor at the offending line, power budget view (the same tables as the reports), threaded export, and the unit-aware power-mode table editor (cells accept "2500 mW"; saving writes canonical YAML, D-028). DOCX reports stay in M4. | Delivers the spec's Views for the static power budget in one PR. |
| D-043 | Offline guard and ReportLab: ReportLab imports `urllib.request`, `http.client` and `ssl` unconditionally (only to fetch images from URLs). The strict import check stays for core, `validate`, XLSX/JSON/CSV and the GUI start-up; the PDF path may import exactly those three modules (whitelist in `tests/offline`), the renderer is imported lazily, ReportLab is restricted to local files and data URIs (`trustedHosts=["localhost.invalid"]`, `trustedSchemes=["file","data"]`), and tests prove no `urlopen` call and no socket use. **Owner to confirm** that importing, but never using, these modules in the PDF path is acceptable for constraint 3. | Constraint 3 literally says "imported"; replacing ReportLab would cost more than it buys. |
| D-044 | Golden tests compare report content (XLSX cell dump, PDF text via pypdf, JSON/CSV text), not compressed bytes, because zlib builds differ between platforms; Python and library versions are pinned in the golden provenance. Byte-identical regeneration is tested separately on one machine (in-process, across processes with different hash seeds, and across seconds). pypdf (BSD) is a dev dependency. | Cross-platform CI must not fail on compression differences. |
| D-045 | openpyxl's `save_workbook` overwrites the workbook's `modified` property with the current time, so XLSX files are written through `ExcelWriter.write_data` and then ZIP-normalised. | Found by a test that renders two seconds apart; constraint 14. |
| D-046 | Config numbers that are real values (not placeholders) are range-checked: margins >= 0, converter efficiency in (0, 1], distribution loss in [0, 1), error `CONFIG_VALUE_INVALID`. | A bad value must be a located problem, not a division by zero. |
| D-047 | The packaged app has a Qt-free `--self-test` (the CLI has `budget self-test`): it parses a unit with pint, computes a budget, renders XLSX and PDF with the bundled fonts. The release workflow runs it on each built bundle. The PyInstaller spec no longer excludes `ssl` because ReportLab imports it (D-043). | Verifies the bundle without a display. |
| D-048 | Mass budget conventions (owner has no convention, so these are my proposal, **owner to confirm**): one right-handed Cartesian spacecraft body frame described in free text in `spacecraft.yaml` (`body_frame`); suggested definition: origin at the centre of the launch-vehicle interface plane, +Z along the launch axis away from the interface, X and Y in the interface plane. All positions are the unit's own centre of mass in this frame, in metres. Inertia entries are tensor entries (Ixy is the tensor element, equal to minus the product of inertia), about the unit's own centre of mass, axes parallel to the body frame. A unit without an inertia is a point mass. | The tool needs one explicit convention; the text field documents the project's choice. |
| D-049 | Mission phases are a user-defined ordered list in `spacecraft.yaml` (`mission_phases`, default one phase named `all`); no phase names are assumed. Units may list `phases` they are present in (default all); expendables give `masses_kg` for every phase (0.0 written explicitly, a missing phase is an error). | Avoids silent zeros. |
| D-050 | CG and inertia use nominal masses of items with a position; items without a position are excluded and reported (`MASS_PROPS_MISSING` with the covered mass share), never counted as zero-position. Mass limits are checked against the system-margined total. | DV-M1, constraint 15. |
| D-051 | `margin_policy` schema v2: `margin_ratio` -> `power_margin_ratio`, new `mass_margin_ratio` per class, `system_margin_ratio` -> `system_power_margin_ratio`, new `system_mass_margin_ratio`; v1 files migrate in memory (new mass values are placeholders). New file kinds: `expendable`, `mass_limits`. | D-034. |
| D-052 | `budget run` gets `--budget power|mass|all` (default all); mass outputs are `mass_static.*`. | Both budgets from one command. |
| D-053 | M3 (environment) conventions: positions are SGP4 TEME in metres, time grid in seconds from the scenario start (UTC); TEME to Earth-fixed uses GMST only (UTC treated as UT1, no polar motion, DV-E1). Sun direction and distance from the Astronomical Almanac low-precision formulae (about 0.01 degree). Shadow: cylindrical (default) or conical via apparent disk overlap (Montenbruck and Gill, Satellite Orbits, 3.4.2). Eclipse intervals are where sunlight ratio < 1 (conical: penumbra included), umbra intervals where it is 0. | Standard, testable models; no own propagator (spec). |
| D-054 | **Definitional physical constants** (WGS-84 Earth radius and flattening, IAU nominal solar radius and astronomical unit) are shipped in code with a `source` string each, not as TBD placeholders; Earth radius and gravitational parameter come from the `sgp4` library's WGS-84 set so geometry and propagation agree. **Owner to confirm** this reading of constraint 15 (it targets margins, standards tables and similar policy numbers, not the definition of the Earth ellipsoid). Project policy numbers stay placeholders. | Without them no eclipse or pass can be computed. |
| D-055 | Orbit sources: `orbits/<id>.yaml` holds either a TLE (two lines, checksum verified) or mean elements treated as SGP4 mean elements (semi-major axis converted to mean motion by Kepler's third law with the library's gravitational parameter; no drag, DV-E2). SpaceMissionStudio import reads an **interim file format** (docs/ENVIRONMENT_FORMAT.md) because no sample export is available; the format is also written by `export_spacemissionstudio` so both adapters can be compared. **Replace the interim format when real samples arrive.** | Spec: import primary, propagator fallback; no sample files supplied. |
| D-056 | Scenario layering: `default_mode`, then `rules` in listed order (later wins), then manual `segments` (hand-built wins). Rule kinds: `during_pass` (a site: ground station or imaging target, optional lead and lag in seconds), `in_eclipse`, `in_sunlight`. Sites live in `ground_stations/` and `targets/`; ids must be unique across both. | Spec: scenarios built by hand or generated from rules. |
| D-057 | Pass and eclipse times are found on the scenario grid and then refined by bisection (about 1 ms), so results do not depend on the grid step. Scenario files hold only parameters; results are never stored in the project. | Accuracy independent of resolution; clean diffs. |
| D-058 | M3 is split into M3a (core, CLI, examples: this PR) and M3b (GUI scenario view with the timeline editor). Runtime dependencies added: `numpy` and `sgp4` (MIT; sgp4 ships an abi3 wheel with a compiled accelerator; the PyInstaller spec lists `sgp4.vallado_cpp` as a hidden import). SciPy is not used: bisection and golden-section search are a few lines. | Smaller dependency set; GUI is a separate review. |
| D-059 | Equations reproduced from memory (Sun low-precision formulae, conical shadow) are registered with `SOURCE_MISSING` and a note that they were checked numerically (published equinox and solstice instants, geometric limit cases) and need verification against the cited texts by the owner. | Constraint 16: flag what is not sourced from the text. |
| D-060 | M3b GUI conventions: the scenario environment is computed in a worker thread; editing rules, segments, the default mode or the name only rebuilds the timeline from the existing environment (reused while `environment_key` is unchanged); changing orbit, sites, times, step or shadow model marks results stale and asks for Compute. Shift+drag on the timeline adds a manual segment. The editor edits default mode, shadow model, sites, rules and segments; orbit, start, duration and step are edited in the YAML (or the YAML tab). Saving writes canonical YAML (comments are not kept, D-028). Unsaved scenario edits are kept across a project reload and block closing like other editors. | Keeps heavy recomputation explicit and rule editing instant. |
| D-061 | **Time-domain power model (M4).** Per step: array output `P_gen = E * sum_faces(N_cells * max(0, cos theta)) * A_cell * eta_ref * k_T * (1 - l_pack) * (1 - l_harness) * k_age * f_lit`, demand `P_dem` at the source (static per-mode source power, D-040, averaged exactly over the step), and an energy-based battery (`E_cap = C_cell V_cell N_s N_p (1 - fade)^years`; surplus charges with `eta_c`, deficit discharges with `1/eta_d`, full and empty saturate and report curtailed and unmet power). Two cases from the same inputs: **BOL** (no degradation or fade) and **EOL** (the design life applied). Demand basis `nominal` (default; `P_eff` through converter and distribution losses) or `margined` (unit and system margins); the report and file state the basis. Every electrical number is `Sourced`; the tool ships no values, placeholders give n/a. Equations are `TDP-*` in the registry, all `SOURCE_MISSING` (textbook relations, owner to confirm). | Spec: array and battery models, SoC over the timeline. |
| D-062 | Inputs live in one optional file `config/power_system.yaml` (`kind: power_system`, v1): `design_life_yr`, `solar_array` (faces with body-frame normal, strings and cells per string; irradiance, cell area, efficiency, temperatures, temperature coefficient, packing and harness loss, annual degradation), `battery` (cell capacity and voltage, series and parallel counts, efficiencies, annual fade, initial state of charge, allowed depth of discharge per mission phase), `attitude`, `limits.peak_power_w`. A project without the file gets no warning for the static budgets. `scenario` goes to schema **v2** with an optional `mission_phase` (selects the allowed depth of discharge; a project with a single phase uses it; v1 files migrate unchanged). New unit suffixes: `_perk` (1/K), `_m2`, `_wm2`, `_ah`, `_yr`. | Schema changes need a version bump and a migration (CLAUDE.md). |
| D-063 | Integration: steps are the scenario grid (`env.grid`), closed at the scenario end. Sunlight and mode changes happen between samples, so each step uses the **exact overlap** with the eclipse intervals (sharp shadow) and with the mode segments (demand); a soft (conical) shadow uses the trapezoid of the sunlight ratio at the step ends. Powers are step averages; battery state is the value at the step edges and saturation is exact inside a step. The Sun direction and the pointing mode are taken at the step start. | Results do not jump when a boundary falls between samples; the error left is one step at a boundary. |
| D-064 | Attitude: each spacecraft mode is `sun` (the Sun is at the fixed body direction `sun_direction_body`) or `nadir` (body frame equals the local orbital frame: +Z to the Earth, +X along the velocity, +Y opposite the orbit normal), per mode in `attitude.by_mode` with an optional `attitude.default`. A used mode without pointing makes the generation n/a. Perfect pointing, no albedo, constant irradiance and one array temperature (DV-P2, DV-P5). **The owner was asked about the pointing convention and had not answered; this is the proposal, easy to extend (spin, fixed inertial).** | Covers charging (sun) and imaging or downlink (nadir) without inventing a pointing law. |
| D-065 | Orbits for the balance check are found from the position vectors alone (revolutions of the angle in the orbit plane), so they work for every environment source and for equatorial and polar orbits. Only complete revolutions count; the first starts at the scenario start. Orbit balance is `integral(P_gen - P_dem) dt` at the source; negative is a violation. The stored-energy change over the orbit is reported next to it (it also contains the battery losses). | Spec: negative energy balance over an orbit. |
| D-066 | Violations (errors, per case, with start and end): `BATTERY_DOD_EXCEEDED` (limit of the scenario's phase; crossing times interpolated linearly between steps), `BATTERY_DEPLETED` (demand not supplied), `ORBIT_BALANCE_NEGATIVE`, `PEAK_POWER_EXCEEDED` (the mode's peak at the source, sum of unit peaks through the losses, above `limits.peak_power_w`, over the mode's timeline segments). The Problems list gets one entry per kind and case with the count and the first time; the full list is in the Violations table and the exports. Each names the input to change (file and path) for the jump link. | Spec: violations with time stamps and jump links. |
| D-067 | **DOCX** reports (python-docx, bundled template, runtime dependency; lxml comes with it) for every budget: `budget run --report docx` and the GUI export. Same neutral `ReportDocument` as XLSX and PDF, which now also carry figures. Core properties carry the provenance time and the ZIP is rewritten with fixed order and time, so regenerated files are byte-identical. python-docx reads its templates through `<package>/parts/../templates`, which only resolves when the package's `.py` files exist in the PyInstaller bundle, so the spec collects them (found by the bundle self-test, which now renders a DOCX with a plot). | Spec: reports in PDF, DOCX and XLSX; D-042. |
| D-068 | Plots: one neutral `PlotSpec` (panels, series, limit lines, shaded bands) drawn by a `QPainter` widget in the GUI (zoom, pan, hover cursor with readout, pinned second cursor with differences) and rendered to PNG with Pillow and the bundled IBM Plex fonts for the reports. No Matplotlib or pyqtgraph: smaller bundle, fewer licences, same look everywhere. `pillow` is declared as a runtime dependency (ReportLab already requires it). Long series are reduced to a min/max envelope per pixel so peaks stay visible. | Spec: plots with cursors and shading; bundled plotting only. |
| D-069 | Outputs: `budget power-timeline` writes `power_time_<scenario>.xlsx/.pdf/.docx/.json` and `power_time_<scenario>_bol.csv`, `_eol.csv` (one row per step, state at the step start, empty cell = n/a; `--series-every N` thins it), `_violations.csv`, `_orbits.csv`. Exit code 1 when there is a violation. A fourth example, `cubesat_3u_eps`, has **invented** round values for margins, converters, array and battery (source text says so) so the budget shows results; its mass numbers and the other three examples stay placeholders. | Constraint 15 and a demonstrable M4. |
| D-070 | GUI: tab **Power timeline** (scenario, demand basis, BOL/EOL, shading, Compute, Export). The run happens in a worker thread and reuses the Scenario tab's environment while it is current. Violations are listed, clicking one zooms the plot and double-click opens the governing input at its line; the Problems panel shows violations and gaps together with the project problems. A project change marks the result stale. | Spec: result plots, Problems panel with all violations, jump links. |
| D-071 | **Thermal conventions (M4b).** Heat dissipated by a unit in a power mode = `avg_power_w * duty_cycle_ratio * heat_dissipation_ratio` (peak: `peak_power_w * ratio`). The ratio is a field of the power mode, **never assumed**: 1.0 unless the unit radiates RF or exports power; a power mode without it makes every thermal result that needs it `n/a` and gives a `RESULT_INCOMPLETE` warning per unit. `unit` goes to schema **v2** (optional `heat_dissipation_ratio` per power mode, `thermal_node`, `temperature_limits`; v1 files migrate unchanged). Units sit on thermal nodes: `thermal_node`, default the node named like the subsystem (D-039); an unknown node is an error. Roll-ups by unit, subsystem, node and spacecraft mode, average and peak. Equations are `TH-*` in the registry, `SOURCE_MISSING` (textbook relations, owner to confirm). | D-036, D-037, D-039. |
| D-072 | The **Stefan-Boltzmann constant** (5.670374419e-8 W m^-2 K^-4) is shipped in code with its source (exact in the 2019 SI, derived from h, k, c; a test recomputes it from them), like the geodesy constants in D-054. **Owner to confirm** with D-054. No flux, optical property, conductance or case definition is shipped. | A definition, not a policy number; without it no temperature can be computed. |
| D-073 | Thermal inputs are two optional config files (no `CONFIG_MISSING` warning when absent): `config/thermal_model.yaml` (nodes, conductances in W/K, surfaces with area, infrared emissivity, solar absorptivity and per-case view ratios; optional reserved node heat capacity) and `config/thermal_environment.yaml` (space temperature, required temperature margin, named cases). Every number except surface areas is `Sourced`. This replaces the `thermal/model.yaml` location in the plan. New unit suffixes `_wk` (W/K) and `_jperk` (J/K). | One place for config numbers; same placeholder rules as the other configs. |
| D-074 | Cases are named by the user (typically hot and cold). Each case picks the spacecraft mode whose dissipation is applied, a `limit_set` (`operating` or `survival`, default operating) that selects which unit limits it is checked against, and the environment: solar flux, albedo, Earth infrared. A surface gets view ratios (share seeing the Sun, share seeing the Earth) per case; absorbed heat is `A (alpha f_sun S + alpha f_earth a S + eps f_earth E_IR)`. A missing exposure for a case is incomplete, not zero. | D-039 (cases are entered, not invented). |
| D-075 | Steady state: `sum_j G_ij (T_j - T_i) + sum eps sigma A (T_space^4 - T_i^4) + Q_i = 0` solved by damped Newton iteration in NumPy (no SciPy). Every connected group of nodes needs a radiating surface, otherwise there is no equilibrium and the case gets `THERMAL_SOLVE_FAILED` naming the nodes. The residual is reported. Transient analysis stays out of v1. | D-058: keep the dependency set small. |
| D-076 | Findings: `THERMAL_LIMIT_EXCEEDED` and `THERMAL_MARGIN_INSUFFICIENT` (the required temperature margin from config; only when it is not a placeholder) are errors, `THERMAL_NO_LIMITS` a warning per unit without limits for the case's set, `THERMAL_NODE_UNKNOWN` and `REF_UNKNOWN_CASE` load errors. `budget run --budget thermal` (also part of `all`) writes `thermal_static.xlsx/.pdf/.docx/.json` and CSV files (dissipation per mode, node temperatures per case); the GUI gets a **Thermal budget** tab with the same tables and the findings in the Problems panel with jump links. All examples carry invented heat dissipation ratios (unit data, 1.0 except transmitters) and a thermal template with `TBD` numbers; `cubesat_3u_eps` has complete invented values and shows one margin finding (the radio in the hot case). A list of candidate reference sources for a thermal engineer to verify is in `docs/THERMAL_SOURCES.md`; no value from them is entered. | Constraint 15; D-039. |
| D-077 | **Link budget conventions (M5).** One file per link and direction in `links/<id>.yaml` (`kind: link`): peer ground station (or none, for static points only, e.g. an inter-satellite link), frequency, transmitter (RF power, line loss, antenna), receiver (G/T given, or antenna + system noise temperature + feed loss), modulation and coding, a list of data rates, required margin, pointing, polarisation and implementation losses, optional named attenuations, optional active spacecraft modes, optional tracking limit (`max_elevation_deg`), static points (elevation and range pairs you choose). Equations `LNK-*`: EIRP = P - L_line + G; L_fs = 20 log10(4 pi d f / c); G/T = G - L_feed - 10 log10 T_sys; C/N0 = EIRP - L_fs - L_other + G/T - 10 log10 k; Eb/N0 = C/N0 - 10 log10 R_b; margin = Eb/N0 - Eb/N0 required. | D-097 | **Step-independent power solve (audit follow-up; refines D-063).** The battery is integrated on the scenario grid refined by every eclipse edge and mode-segment edge, so a coarse step no longer averages a discharge away (the maximum depth of discharge of a 1750 s eclipse was 0.133 at a 300 s step but 0.05 at 1200 s; it is now the same at every step). | D-098 | **Numerics follow-up (audit).** *Units:* an angle unit (`rpm`, revolutions, radians, degrees per second) in a field that is not an angle is refused (pint reads 60 rpm as 2 pi rad/s, which became 6.283 Hz); Celsius or Fahrenheit below absolute zero is refused in a `_k` field, while a plain negative kelvin value stays possible because margins are differences. *Thermal:* a solution is accepted only when every node balances to 1e-9 of the heat flowing through the body or to the rounding of its conduction terms (a small step alone no longer ends the iteration), and a network whose conductances are so large against the radiation that double precision cannot resolve the temperatures to 0.1 mK gives `THERMAL_SOLVE_FAILED` with that reason instead of a wrong number.
