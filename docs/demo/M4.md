# M4 Time-domain power budget — demo note

```
budget export-examples demo
budget power-timeline demo/cubesat_3u_eps --out out      # BOL and EOL, reports, CSV, JSON
system-budget-studio demo/cubesat_3u_eps                 # tab "Power timeline", press Compute
```

`cubesat_3u_eps` is the 3U example with **invented** round values for margins, converters, array and battery (their source text says so), so you see results. The other three examples keep every number as a placeholder; run `budget power-timeline` on them and the results show **n/a** with a `RESULT_INCOMPLETE` entry for every missing input (never a silent zero).

What the command prints for the example: generated energy and lowest state of charge per case, and the finding the example is built to show: **the peak power at the source (7.96 W during downlink and imaging) is above the 7.5 W limit** in 12 intervals, each with its start time and the input to change (`config/power_system.yaml: limits.peak_power_w`). Exit code 1 means a violation; warnings (placeholders) only fail with `--strict`.

In the window:
- **Plot** (three panels: power with the peak limit, state of charge with the minimum allowed, margin) with eclipses (grey) and each site's passes shaded. Wheel zooms around the pointer, drag pans, double-click shows everything. Hovering shows a cursor with the time, UTC, spacecraft mode, eclipse state and every value; a click pins a second cursor and the readout then shows the differences; Escape or a right click unpins.
- **Violations** table: selecting a row zooms the plot to that interval, a double click opens the file that governs it at the field. The same findings, with the first time and the count, are in the Problems panel.
- **Summary**, **Orbits** (energy balance per complete orbit) and **Modes** tables; the case selector switches BOL and EOL without recomputing; the demand basis (nominal or with margins) is chosen before Compute.
- Compute runs in a worker thread and reuses the Scenario tab's environment when it is current. Editing an input marks the result stale.
- File > Export power timeline writes `power_time_<scenario>.xlsx|pdf|docx|json` and the CSV files (series per case, violations, orbits).

Files: `config/power_system.yaml` (array, battery, attitude per mode, peak limit; format in `docs/FILE_FORMAT.md`), `mission_phase` in the scenario (schema 2; a v1 scenario migrates unchanged). DOCX is also available for the static power and mass budgets: `budget run --report docx`.

Verified against hand calculations: temperature and degradation factors, a full array power chain, cosines on several faces, battery capacity with fade, charge and discharge efficiency, saturation at full and empty, orbit windows, exact sunlit share with an eclipse off the grid, orbit energy balance, the timing of a depth-of-discharge violation (4350 s to 5100 s in the test case), peak-power intervals, the nadir-pointing average of 1/pi, converter and distribution losses, margins, and a real SGP4 orbit against the closed-form eclipse fraction.

Performance: one week at 1 s with 200 units, conical shadow, three sites and both cases: about 5 s end to end (about 4 s environment, 1 s power); the series CSV of that week (604,800 rows) takes about 5 s to write.

Tests: new regression (29 cases), property tests (Hypothesis: more array area never reduces generation, stored energy stays between empty and full, energy is conserved, more generation never lowers the stored energy), model and validation tests, report and golden tests for XLSX/PDF/DOCX/CSV/JSON, CLI, offline, GUI.

Open for the owner (new): the attitude convention (D-064) and the demand basis default (D-061) are proposals; equations `TDP-*` are `SOURCE_MISSING` until you give the reference text; real array and battery numbers, margins, converter efficiencies and the allowed depth of discharge per phase. Still open from earlier: SpaceMissionStudio samples, D-043, D-048, D-054, D-059, the repository being public, and branch protection. Next is M4b (thermal budget).
